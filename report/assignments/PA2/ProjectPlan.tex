\section{Introduction}
This Software Development Plan describes how the OmniCourse team of five students organises, schedules and controls the
development of the product in the course project. The project runs for twelve weeks, from 5 October to 13 December 2026,
organised as five two-week sprints inside three RUP phases. The document defines the purpose and scope, the team
organisation and roles, \chg{the effort estimates,} the phase and iteration plan, the planned releases, the schedule, the
resourcing, and the reporting, \chg{risk management} and configuration management processes. \chg{Version 2.0 is written at
the end of Sprint 2, the first Elaboration sprint, with the requirements baseline in hand.}

\section{Project Overview}
\subsection{Project Purpose, Scope, and Objectives}
OmniCourse is a public web application that gives an HCMUS student one page for everything school related: degree audit,
curriculum explorer, semester roadmap planner, an AI-assisted planner and advisor, and the exact links and steps for the
school tasks the application does not perform itself. The first release covers the Advanced Program in Computer Science
(APCS); the model is program-agnostic, so other HCMUS majors and later other Vietnamese universities are added as
configuration.

The objectives of the project are:
\begin{enumerate}
  \item a deployed, working web application that covers the APCS curriculum;
  \item a deterministic rule engine that enforces prerequisites, offering terms, requirement coverage and the credit caps
        of the program, so that no academic rule is decided by a language model;
  \item \chg{a plan generator that turns a planning goal, given in a form or in the student's own words, into a plan built by
        a deterministic planner over that engine, and explains every placement. A model only turns the student's words into
        the form's fields (ADR 0003);}
  \item a curriculum data model that can be reused for another program or another school without changing the engine.
\end{enumerate}

Out of scope for this course: native mobile applications, automation of the school registration portal, storage of portal
credentials, \chg{reading transcripts or curriculum documents with a language model,} and the optional modules (tuition,
conduct score, paperwork, community).

\subsection{Assumptions and Constraints}
\begin{itemize}
  \item Fixed schedule: five sprints of two weeks, 5/10/2026 to 13/12/2026, aligned with the course plan agreed in PA0.
        No extension is possible.
  \item Team of five students, no member added or removed during the project.
  \item \chg{Budget: free tiers for hosting and CI. The model API is paid, for privacy, and capped by a monthly spending
        limit (§4.1).}
  \item Expected effort is at least 10 hours per member per week, about 50 hours per week for the team.
  \item All five members are full-time students, so lecture and examination weeks reduce capacity.
  \item The process is fixed by the course: three RUP phases, five Scrum sprints, and the tools approved in PA0 (Moodle,
        Discord, GitHub).
  \item No official API exists for the HCMUS curriculum or the student record, so curriculum data is entered and verified
        by the team, and the transcript is a file the student uploads.
  \item The academic rules follow Thông tư 08/2021/TT-BGDĐT and the published HCMUS credit caps. Personal data follows
        Luật 91/2025/QH15.
  \item The application never stores a portal password and never automates a registration on the student's behalf.
\end{itemize}

\section{Project Organization}
\subsection{Organizational Structure}
The team has a flat structure of five members. The project lead coordinates the plan, the schedule and the sharing of work,
and is the single contact with the instructor and the TAs, who review and grade each assignment and may request changes to
the scope. Two technical leads own the frontend and the backend workstreams and review the pull requests of their side; the
two remaining members carry the testing duties. The stack, the data model and the scope of each sprint are decided together
in the weekly meeting, and the project lead breaks a tie.

\subsection{Roles and Responsibilities}
All five members write code, so every member is a Developer. \chg{Each member owns a slice of the product end to end (use
case, design, backend module, frontend pages, tests and the sprint demo) and keeps it for the whole project, so no feature
changes hands mid-build. Every code folder, database table and document has exactly one owner, and modules call each
other only through agreed contracts.}

\subsection{Project Monitoring and Control}
\subsubsection{Reporting}
Status is reported in three ways. First, a weekly report every Sunday, written on the course template \chg{and stored in
\texttt{/report/weekly}}: it lists what was completed, what slipped, the issues and the goals of the following week. Second,
a weekly meeting of about thirty minutes at the start of each week, where the report is closed, the priorities of the sprint
are confirmed and any blocker is assigned to a person. Third, continuous status in the project Discord server: every task's
owner moves it through \chg{Bucket, Doing and Done} on the day it changes and adds the pull request number. \chg{A decision
that outlives one pull request is recorded as an ADR in \texttt{/docs/analysis-and-design/adr}; ten are recorded so far. A
handoff that slips is reported in the weekly report of the week it slips.}

\subsubsection{Configuration Management}
Source code and documents live in one GitHub repository owned by the team: \texttt{/src} for the code,
\texttt{/docs/management} for plans, \texttt{/docs/requirements} for the vision and the use cases,
\texttt{/docs/analysis-and-design} for the architecture, the models, the UI prototypes \chg{and the ADRs},
\texttt{/docs/test} for the test plan and cases, and \texttt{/report} for the submissions.

\begin{itemize}
  \item No one pushes to main. Every change arrives as a pull request \chg{from a branch named
        \texttt{<type>/<short-name>}}.
  \item \chg{CI enforces the rules: typecheck, tests and build of both sides, backend e2e tests against PostgreSQL, every
        commit signed, Conventional Commit messages and PR titles, and a changeset in every pull request.} A pull request
        merges only when CI passes and at least one other member has approved it.
  \item \chg{The Project Lead may use the admin override for urgent fixes or tie-breaks, and says why in the PR.}
  \item After approval the author merges \chg{(squash merge)} and deploys.
  \item Review duty follows the workstream: the frontend lead reviews frontend work, the backend lead backend work, and the
        project lead the data model and the rules.
  \item \chg{Changesets build a release pull request that bumps the version and writes the changelog; it is merged at the
        end of each sprint, and the build is tagged B0 to B3.}
\end{itemize}
