# ADR 0010: Public pages and guide content

- Status: accepted
- Amends: [ADR 0002](0002-authentication-and-sessions.md)
- Date: 2026-10-30
- Owner: Dũng (F9 sharing, F11 guides)
- Deciders: Lâm (Project Lead), accepted 30 Oct 2026
- Reviewers: Hoà (`plans` API), Triết (Backend Lead)

## Context

[ADR 0002](0002-authentication-and-sessions.md) makes every route require a signed-in user unless it is marked `@Public()`. Today only three routes are public: health, sign-up and sign-in. Two features need pages that anyone can open:

- F9: a lecturer or academic advisor opens a student's shared plan from a link (UC-09). Most will not have an OmniCourse account.
- F11: guides hold only what the school publishes, so a student can read them before signing up (UC-10).

F11 also needs a place to keep guides that records every version (Vision F11: "Every guide is versioned").

The shared-plan route also crosses a module boundary: F9 is Dũng's, but plans belong to Hoà's `plans` module.

Lâm decided these points on 30 October 2026, in answer to Dũng's questions on UC-08 to UC-10. The same day Lâm confirmed two details: public pages only read, and a test catches any route made public by mistake.

## Decisions

| Decision | Alternatives rejected | Evidence |
| --- | --- | --- |
| **Guides can be read without signing in.** The routes that list, search and return a guide are `@Public()` and only read. The parts of a guide that use the student's data (the program's values from the rule engine, the courses of a plan) and **Report a problem** stay behind sign-in. | Keep sign-in for guides (ADR 0002 default). Make problem reports public too. | A guide holds no personal data, only what the school publishes. A public write would invite spam, with no user to rate-limit or trace. UC-10 A3, A4, A6. |
| **A shared plan opens without signing in.** One `@Public()` read route takes the link's token and returns only the content listed in UC-09 step 2. The token is 32 random bytes, like a session token. A stopped, deleted or unknown link gets the same "not shared" answer. The page tells search engines not to index it. | The reader must sign in. The student invites the reader by email. | Vision F9 shares the plan "with an academic advisor", who should not need an account. A 32-byte token cannot be guessed (ADR 0002). One answer for every dead link means the page does not reveal whether a plan exists. |
| **The shared-plan route lives in Dũng's own `sharing` module.** It reads plans only through a read-only method that Hoà's `PlansService` exports. | A route inside Hoà's plans controller. | One folder, one owner (Work Breakdown rule 2, as in ADR 0003). The public route can reach no write in the `plans` module. |
| **Guides are content files in the repository, loaded into the database by a seed.** One file per guide and language. There is no admin screen. A guide removed from the files is withdrawn, not deleted, so problem reports about it stay valid. | An admin screen like curriculum administration (UC-11). Editing guides straight in the database. | Git records every version and who changed it. Each change gets a second person's review in a pull request (guides plan §6). An admin screen would need its own permissions, which F11 has no time for: the whole feature is estimated at 10 hours (SDP v2 draft, PR #20). |

### Shared plans as built (amended 25 November 2026)

The API of F9 was built on 25 November 2026 (`src/backend/src/sharing/`). The points below are what the first table left to the implementation. They were chosen in the implementation pull request. Three of them were open questions: what a reader sees of the checks that come from the transcript, how the token is stored, and where the PDF is made. Dũng, the owner of F9, answered the three on the team Discord on 25 November 2026; the answers are marked "agreed by Dũng" below. **The Project Lead accepts or changes every point of this amendment in the review of that pull request.**

| Decision | Alternatives rejected | Evidence |
| --- | --- | --- |
| **Routes.** The owner: `GET`, `PUT` and `DELETE /api/plans/{id}/share`, behind sign-in, for their own plans only. `PUT` shares the plan: a plan not shared gets a new link, a plan already shared keeps its link. `PUT` also carries the owner's two choices for the link, `showName` and `showTranscriptChecks`, under one rule: only an explicit `true` turns a choice on, an explicit `false` turns it off, and a choice left out stays as it is (off on a new link). A choice that is sent must be a boolean (`null` is refused), and the body is a JSON object or absent (an array is refused). The reader: `GET /api/shared-plans/{token}`, the one `@Public()` route of the module. | `POST` to create and `PATCH` to change a choice; the token in a query string; a choice left out counts as `false` | One idempotent request covers "Create link", "the plan is already shared" (UC-09 A4) and both tick boxes: two requests at once end with one link. A page that sends one choice cannot change the other by accident, and no choice turns on without an explicit `true`. Another student's plan answers 404, as in ADR 0014. |
| **One table, `plan_shares`, with at most one row per plan (`UNIQUE (plan_id)`). Stopping a link deletes its row.** The row has its own `user_id … ON DELETE CASCADE` and the composite key `(plan_id, user_id) → plans (id, user_id) ON DELETE CASCADE`, as `plan_placements` has. | A `revoked_at` column that keeps stopped links; a column on `plans` | With no row, a stopped link, a deleted plan, a deleted account and a link that never existed are the same lookup with the same answer (UC-09 A2, A6, A8). Nothing about old links is kept. Export and purge cover the table with no extra code (ADR 0004). |
| **The token is 32 random bytes in base64url, from `crypto.randomBytes`, and it is stored readable** in `share_token`. *Agreed by Dũng, 25 November 2026.* | Store only its SHA-256, as for a session token (ADR 0002); encrypt it with a server key | UC-09 A4 shows the live link again later, which a hash cannot do. A server key would be a new secret to deploy and rotate. The name ends in `_token`, so the account export never selects it. **Cost:** someone who reads the database can open every shared plan, though not the grades or the account behind it. The token is also in the path of the URL, of the API and of the page, so a proxy's access log holds it: someone who reads those logs can open the plans that are still shared. |
| **The reader's answer is built field by field** (`sharing/shared-plan.ts`): the plan's name, the curriculum code, cohort and names, the program, the last change, each term with its courses (code, names, credits), slots (group name, credits), load and caps, the issues below, and the owner's display name only when `show_name` is true. It holds no id of the plan, the owner, the curriculum or a requirement group: where the engine's report names a requirement group or a combined minimum by id, the answer gives its name. | Return `PlanDto` and the engine's report as they are | UC-09 step 2 and §7 list what a reader sees. An e2e test compares the full set of keys at every level, with the choice below off and on, so a field added later fails until someone allows it. |
| **The owner chooses, for each link, whether a reader sees the checks that come from the owner's transcript. The choice is off unless the owner turns it on** (`show_transcript_checks`, sent as `showTranscriptChecks`), and it can be changed on a live link without a new link, like the name. The issues always come from the rule engine (`PlanIssuesProvider`). **Off:** the answer holds the ten issue codes that follow from the plan and its curriculum alone, and names the four it leaves out in `issueCodesNotShown`: `prerequisite_not_met`, `already_passed`, `already_in_progress` and `requirement_not_covered`. The transcript is then not read at all: the engine checks the plan with an empty transcript (`issuesWithoutTranscript`) and is not told whose plan it is. **On:** the answer holds the same issues as the owner's own `GET /api/plans/{id}/issues`, the four codes included, and the engine's coverage of each requirement with the graduation status (`coverage`); `issueCodesNotShown` is empty. On or off, the answer holds no grade, no transcript row and no id. *Agreed by Dũng, 25 November 2026, with six conditions, listed below.* | Always show every issue the owner sees (UC-09 A9 as first written); never show the four codes; with the choice off, run the engine with the transcript and drop the four codes afterwards; show what the engine reports without the transcript | Each of the four codes, by being there or by being absent, tells a reader which courses the owner has passed, failed or is taking, so showing them is the owner's decision to make, and a link made without a decision shows none. An advisor who gets a link with the choice on sees the two findings that matter most for a review, a missing prerequisite and a requirement not covered. With the choice off, reading the transcript and dropping the four codes gives the same answer, but the time the answer takes then depends on the transcript; not reading it removes that too. The engine without the transcript reports passed prerequisites as not met and passed requirements as not covered, which would be wrong verdicts under the engine's name if shown (AGENTS.md hard rule 1). They are never shown: those verdicts are exactly the four codes and the coverage, which the answer leaves out when the choice is off. What is shown then (the ten codes, the loads and the caps) is the same with and without the transcript. Tests: the engine's two checks agree on everything but the four codes and the coverage (`rules.service.spec.ts`); with the choice off, the reader's answer equals the owner's own report without the four codes, saving a transcript leaves it exactly the same, and the transcript is not read; with it on, the reader's issues and coverage equal the owner's, and no grade value or transcript wording is anywhere in the answer; turning it off restores the earlier answer on the same link (`shared-plan.spec.ts`, `plan-sharing.e2e-spec.ts`). Both lists of codes are written by a person, so a code the engine gains later reaches no reader until someone classifies it. |
| **No estimated graduation term: a recorded gap.** UC-09 step 2 and UC-16 list it, and no answer holds it, with the choice on or off. | Work one out in the sharing module | Nothing in `src/` computes one ([design differences](../design-differences.md), UC-03 and UC-05), and a module other than the rule engine must not (hard rule 1). When the rule engine computes one, it reads the transcript, so it belongs under the same choice. |
| **A deletion request deletes the account's `plan_shares` rows in the same transaction that revokes the sessions.** The public read also refuses an account that is waiting for deletion, and `PUT …/share` locks the account's row, so a share request that crosses a deletion request leaves no link. | Only check `deletion_requested_at` when a link is read | UC-09 A7: the links stop at once and stay stopped when the account is restored. A check at read time alone would bring the links back on restore. |
| **Every answer with a body under `/api/shared-plans` carries `X-Robots-Tag: noindex, nofollow` and `Cache-Control: no-store`:** the plan, the "not shared" 404, the rate limit's 429, and the framework's own 400 for a path that cannot be decoded and 404 for a longer path or another method. A middleware on the path prefix sets them (`sharing/shared-plan-headers.ts`); it runs before the guards and before the route is matched. The one answer without them is the CORS answer to an `OPTIONS` request: the CORS handler of the whole API answers it first, with status 204 and no body, so it holds nothing to index or to cache. A token that is not 43 base64url characters is answered without a database query. | A header only on the 200; headers set in the route handler, which miss the answers the handler never makes | UC-09 §7 asks for `noindex`; a cached answer would outlive a stopped link (A2). `plan-sharing.e2e-spec.ts` and `rate-limits.e2e-spec.ts` check each of these answers. The page itself must add its own `noindex`: the API's header covers only the API's answers. |
| **No PDF on the server: the PDF is the browser's print layout of the page.** *Agreed by Dũng, 25 November 2026.* | A PDF library in the API | UC-09 A1 keeps no file on the server, and the prototype prints the page (`print()`). A server PDF needs a new dependency. The owner's own PDF (A1) follows the same choice about the transcript's checks as the link. |

Dũng's six conditions for the owner's choice (team Discord, 25 November 2026), and where each one is met:

1. *When the choice is on, the Share panel tells the student plainly that a reader can tell which courses they passed or are taking.* A requirement for the screen, not built here. The review of the implementation pull request found that a failed attempt shows too: when a course on the board is failed in the transcript, the engine reports the course that needs it and the requirement that holds it as not met, to the owner and so to the reader. The warning text therefore says "passed, failed or are taking". The owner's `GET` and `PUT` answers give `showTranscriptChecks`, so the panel can show the state and the warning.
2. *When it is off, the page keeps "some checks are not shown".* `issueCodesNotShown` names the four codes when the choice is off and is empty when it is on. The page must say that these checks are not shown whenever the list is not empty.
3. *It can be changed on a live link without a new link, like the name.* Built: `PUT` keeps the token.
4. *UC-09 §7 and A9 are reworded to match.* Done in UC-09, with step 2, A1 and the list of decisions.
5. *The owner's PDF (A1) follows the same choice.* A requirement for the screen: the PDF is the print layout of the same content.
6. *The estimated graduation term and the requirement coverage also come from the transcript: under the same choice, or recorded as gaps.* The coverage and the graduation status are under the choice (`coverage`). The estimated graduation term is the gap in the table above.

Still for the Project Lead, in the review of the implementation pull request: to accept or change the owner's choice and its default, the readable token, and the browser PDF. None of the three is the Project Lead's decision yet.

## Consequences

- After this ADR, five kinds of route are public besides the API docs pages: health, sign-up, sign-in, reading guides and reading a shared plan. Anyone can open them, but nobody can change anything without signing in. The one exception is sign-up and sign-in themselves, which must stay open or nobody can get in. Every other route stays default-deny, and a new public route needs a change to this ADR.
- `src/backend/test/public-routes.e2e-spec.ts` takes the OpenAPI document of the whole app, calls every route without a token and expects 401, except for the routes on its allowed list. It also fails:
  - if a listed route is missing or answers 401;
  - if the list holds a write other than sign-up and sign-in;
  - if the document lacks `GET /api/users/me`, so the 401 check cannot pass by checking nothing;
  - if Express serves a route the document lacks, such as one hidden with `@ApiExcludeEndpoint`.

  It runs in CI on every pull request. A new public route fails it until it is added to the list, where reviewers see it. Today the list holds health, sign-up and sign-in; the guides and shared-plan pull requests add their routes. *Since 25 November 2026* the list also holds the two guide reads and `GET /api/shared-plans/{token}`.
- The API docs pages are public too: `/api/docs` with its assets, `/api/docs-json` and `/api/docs-yaml`. `SwaggerModule.setup` serves them outside any controller, so they are not in the document, and the test skips them by path. They only describe the API. They are not served when `NODE_ENV=production` unless `API_DOCS=true` (issue #28).
- Public routes use the global rate limit (120 requests a minute per address). Behind the staging host's proxy, all visitors share one address until `trust proxy` is set (ADR 0002, Deferred). That fix now protects public pages as well as sign-in.
- Hoà's `plans` module exports one read-only method for the `sharing` module. F9 needs it before Sprint 4 (B2). *As built:* `PlansService.find(userId, planId)`, which returns the owner's plan or null and writes nothing; the owner routes check ownership with `PlansService.get`.
- The `account` module imports `sharing`, so that a deletion request stops the links (UC-09 A7).
- Regulation documents for the advisor chat (UC-08) use the same approach, also decided by Lâm on 30 October: files in the `advisor` module, typed by hand and reviewed in pull requests. They are not public pages. *Amended 15 November 2026 (Lâm):* typing by hand, with no AI, stays the rule for the regulation files only. An AI tool may draft and translate guide text; portal addresses, labels and steps still come only from the school's pages or the portal, and no personal data goes into the tool (guides plan §6 step 1).
