# ADR 0020: Module boundaries, their owners and how they are enforced

- Status: proposed
- Date: 2026-11-28
- Deciders: Lâm (Project Lead) asked for the work (28 November 2026: converge the codebase so that one change lands in one place and people and agents can work in parallel). The decisions below are the builder's proposal, so the status stays **proposed** until Lâm accepts it.
- Reviewers: Triết (backend, architecture document), Hoà (frontend)

## Context

AGENTS.md asks for an ADR when a decision outlives one pull request, and names a new module boundary as an example. Until now the boundaries of this codebase were prose: "one Nest module per feature folder", "API calls in `api.ts`", "read settings through `config/env.ts`". Two untangle passes (9 and 26 November 2026) cleaned the structure by hand, and the next large pull request (#207) added cross-module imports that nobody had to decide on: on the backend `curriculum -> curriculum-admin` (which closed a cycle) and `account -> curriculum-admin`, on the frontend `plans <-> sharing`. The backend had the folder cycles `curriculum <-> curriculum-admin`, `curriculum <-> database` and `auth <-> users`. On the frontend the root folder held both the shared leaves and the composition root, so every feature folder was in one cycle with every other.

Several concepts also had no single owner. "This account is waiting for deletion" was read in about ten places in five modules, mostly inside raw SQL. Database lock keys were numbers in three modules. The coded error body `{ statusCode, code, message }` was built by helpers and also by hand. The rule engine took its input types from a Nest injectable and from TypeORM entity files.

This ADR records what the stack of pull requests #220 to #239 decided, so the next change follows it without reading twenty pull requests. The lists themselves are not copied here: `scripts/layers.mjs` is their only home.

## Decisions

| Decision | Alternatives rejected | Evidence |
| --- | --- | --- |
| **An import across folders is a line in a list.** `scripts/layers.mjs` lists every allowed import between backend folders (`backendEdges`) and between frontend feature folders (`frontendFeatureEdges`). `npm run lint` fails on an import whose edge is not listed, and on a listed edge that no code uses any more, so the lists change only on purpose and a reviewer sees the line. Files directly in `src/backend/src` are the composition root and may import anything. Spec files and `testing/` folders may import anything too, and the home rules below do not check them. | A dependency checker such as dependency-cruiser or eslint-plugin-boundaries: a new dependency and a second configuration language, in a repo that has no ESLint and already runs `scripts/lint.mjs`. Prose only: it held for neither untangle pass. Forbidding the existing cycles at once: they needed code changes first; listed, they could not grow meanwhile. | Rules `backend-import-direction` and `frontend-feature-edges` in `scripts/lint.mjs`, each with a failing and a passing case in `scripts/lint.test.mjs`; #220 |

Composition files (`frontendComposition`: `main.ts`, `App.vue`, `router.ts`, the shell frame) may import anything and are imported only by each other. The dashboard inside `audit/`: the degree audit then imports four features and `audit` and `plans` import each other. | The route table is byte-identical before and after (#233, #237); `shell/nav.spec.ts` |

## Accepted exceptions

The three import exceptions are lines in `scripts/layers.mjs`, so they cannot spread without an edit there. The others are design choices that no check enforces.

- **`auth <-> users` (backend).** The users controller uses the auth decorators, and `auth` uses the users service and the `User` entity. Each folder imports the other, but no two files import each other. Moving the decorators would touch about twenty importers for no change in behaviour.
- **`curriculum.entity.ts` and the `program` and `requirement-group` entity files import each other in pairs.** TypeORM relations need both ends. Lint checks imports across folders only, so nothing lists this one.
- **`plans <-> sharing` (frontend).** The plan editor opens the share dialog, and the shared page reuses the plan components.
- **`audit -> plans` (backend).** `CreditCapsDto` (used by `audit` and `sharing`) lives in `plans/plan-issues.dto.ts`. In `rules/` its Swagger decorators would need a special case in the engine's purity check, which allows framework imports only in `rules.module.ts` and `rules.service.ts`.
- **`CapMeter` and `IssueCard` take a `variant`.** The plan editor and the shared plan page differ in nine small style details. They are kept until the frontend owner says whether the two should look the same.
- **`codedError` takes fields before or after the message.** It keeps the key order of the bodies the API already sends.
- **The AI gateway builds its own coded error.** `ai/` is the second entry of `codedErrorHomes`; its files belong to the open advisor pull request (#77).

## Consequences

- A pull request that adds an import across backend folders, across frontend feature folders or against the frontend layers also adds one line to `scripts/layers.mjs`, or `npm run lint` fails. The ruleset does not require a branch to be up to date, so a pull request that was green can still turn `main` red when another one lands first; the fix is that one line.
- A new backend module must be reachable from `features.ts` and named in the module table of architecture.md, or lint fails.
- A write that must stop for an account waiting for deletion calls `users/account-state.ts`; it does not read the column.
- A frontend test cannot mock a route before the route is in `openapi.json`.

## When to look at this again

- When the shared rules package of ADR 0015 is built: the engine vocabulary moves into it and the purity check becomes the package boundary.
- When the open pull request for the advisor (#77) lands: `ai/` should own the shape of its settings, which `config/env.ts` holds today.
- If the repo adopts ESLint: an import-boundary plugin could then replace the import rules of `scripts/lint.mjs`.
- If `frontendFeatureEdges` stops shrinking and most features import most others: the feature folders no longer match how the screens change together.
