### TC-B2-ADM-07: CSV bulk import

A synthetic CSV of courses or group links is parsed deterministically and shown as a preview with errors by row number. A file with any bad row saves nothing, a valid file saves in one transaction after confirmation with the same permission checks as manual entry, and importing it again creates no duplicates ([test plan row](test-plan.md#b2-checks)).

- Owner: Thắng
- Depends on: the CSV import API of [#147](https://github.com/LLaammTTeerr/omnicourses/pull/147) ([ADR 0011, CSV import as built](../analysis-and-design/design-differences.md#csv-import-as-built)); ADR 0011 (accepted). These cases call the API only, on purpose: [#165](https://github.com/LLaammTTeerr/omnicourses/pull/165) added the import screen ([#151](https://github.com/LLaammTTeerr/omnicourses/issues/151)), and no screen case for it is written yet. #147 merged into `main` on 25 November 2026 (`2363714`).
- Group totals stay **blocked** (ADM-07k). Lâm decided on 25 November 2026 that the group-link import ships with the structural checks of the manual route and no group-total check ([ADR 0011, amendment of 25 November](../analysis-and-design/adr/0011-curriculum-administration.md#amendment-25-november-2026-csv-group-links-with-structural-checks-only): "The group-total part of TC-B2-ADM-07 stays blocked"). ADM-07a–j check everything else, so Triết's handoff no longer blocks them.

**How an import works.** Four `POST` routes, each answering **200** on success, under `curriculum-admin` in Swagger:

| Route | Grant | Body |
| --- | --- | --- |
| `/api/admin/catalog/imports/preview` | `catalog_maintainer` | `{ "csv": "…" }` |
| `/api/admin/catalog/imports/confirm` | `catalog_maintainer` | `{ "csv": "…", "reviewVersion": "…" }` |
| `/api/admin/programs/{programId}/cohorts/{curriculumId}/imports/preview` | the program's `program_admin` | `{ "csv": "…" }` |
| `/api/admin/programs/{programId}/cohorts/{curriculumId}/imports/confirm` | the program's `program_admin` | `{ "csv": "…", "reviewVersion": "…" }` |

The file travels as a JSON string: no upload, and the server keeps no file. A preview saves nothing and answers the normalized rows (`action` `insert`, `update` or `no_op`), the row `errors` (`record`, `field`, `message`, where the header is record 1), a `summary` (`inserts`, `updates`, `noOps`) and a `reviewVersion`, which is `null` when the file has any error. The confirmation sends the same file with that `reviewVersion`. It checks the grant again, and saves the whole file in one transaction only if the file and the saved data it touches still give the same version. Otherwise it answers 409 `impact_changed`. Not confirming is the API's **Cancel**: nothing is saved.

## 8. TC-B2-NOTIF-01: Notifications

Registration-window reminders, the term-start check-in and the warning after a saved transcript change reach the right student from the right event, and never come from a cancelled or failed save. Delivery, timing and repeat checks follow the F10 rules that Dũng decided on 25 November 2026 ([test plan §8](test-plan.md#8-schedule-and-remaining-work), [ADR 0018](../analysis-and-design/adr/0018-notification-inbox.md)).

- Owner: Dũng
- Depends on: calendar API (#108); the notification inbox API (#156, #162; on staging since `5a5b9d5`); the inbox screen and unread bell (#204, #205: `NotificationsView.vue`, `UnreadBadge.vue`); [ADR 0018](../analysis-and-design/adr/0018-notification-inbox.md) (accepted 27 November 2026). NOTIF-01a–i call the API, with one screen step in NOTIF-01g; NOTIF-01j checks `/notifications` and the unread badge.

**The rules under test** (test plan §8; ADR 0018, Context). A registration window gives one notification 7 days before it opens (`registration_soon`) and one on the day it opens (`registration_open`); a term start one on its first day (`term_start`); a saved transcript that differs from the saved one gives `transcript_changed`, but not the first import, a cancelled or failed save, or a save with no change. Days are Vietnam days (UTC+7). Each student gets each notification once; a date entered late gives what is due now and skips the days that have passed; a date that moves sends nothing again. A date entered for today, or exactly 7 days ahead, gives its notification at once. Recipients are the students whose saved onboarding program is the date's program, when the notification is made, without the accounts waiting for deletion. A notification is a kind, a copy of the date and link keys, never a sentence, URL, grade or course. Not in B2: add/drop and other kinds of date.

**Accounts and values.** N1, N2 and N3 (§1); A1 and A2 with their ADM-02 grants. `{APCS}` and `{KHMT}` as in ADM-02. **D** is the Vietnam date of the run (UTC+7), written `YYYY-MM-DD`, and `D+n` the date n days later. **A test date** is entered as A1 with `POST /api/admin/programs/{APCS}/calendar-events` and the body `{ "academicYear": 2026, "kind": "<kind>", "startsOn": "<start>", "endsOn": "<end>", "title": "Ngày thử NOTIF-01<x>", "titleEn": "NOTIF-01<x> test date" }`; keep the answer's `id` as `E-<x>`. "The notifications of `E-x`" are the ones whose `event.id` is `E-x`; the cases look at no other notification, because staging's real school dates make their own. "As N1, read" is `GET /api/notifications`.

**Run it in one Vietnam day**, from 00:10 to 23:30 Vietnam time (17:10 UTC the day before to 16:30 UTC on day D), so that "today" does not change in the middle; NOTIF-01d(2) runs on D+3.
